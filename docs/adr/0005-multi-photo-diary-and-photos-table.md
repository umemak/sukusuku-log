# 思い出日記の複数枚写真対応と diary_photos テーブル設計

思い出日記において1投稿あたり最大10枚の写真を添付可能とし、かつ写真グリッド一覧で全写真を個別のタイルとして高速に一覧表示するため、単一の `diary.photo_id` カラムから 1:N のリレーションを持つ `diary_photos` テーブルを新設して順序（`sort_order`）とともに管理する構成を採用した。

## Considered Options

- **`diary` テーブルに `photo_ids` JSON配列を格納**: テーブル追加が不要でスキーマは簡潔だが、グリッド一覧で「全写真を1枚ずつ並べる」要件において SQLite でのインデックス活用やJOIN・ページネーションが複雑化する。
- **代表写真のみグリッドに表示し、子写真はJSONで持つハイブリッド案**: 一覧のクエリは単純化できるが、「すべての写真をグリッドに並べて一覧したい」というユーザー要件を満たせない。
- **既存 `diary.photo_id` のカラムを `photo_id_1`〜`10` のように増設**: 直感的に扱えるが、動的な枚数変更・ソートや削除時の管理が破綻しやすい。

## Consequences

- `diary_photos` テーブルへのインデックス（`child_id, created_at`、`diary_id, sort_order`）により、写真グリッド一覧取得（写真タイル単位のクエリ）および日記詳細時の全写真取得が高速に行える。
- 既存の単一写真データはマイグレーションにより `diary_photos` へ引き継ぎ、下位互換性のため `diary.photo_id` には先頭（代表）写真のIDを同期保持する。
- 写真の削除や日記自体の削除時には、`diary_photos` に紐づく全 R2 オブジェクト（原版およびサムネイル）を一括クリーンアップする責務が発生する。
